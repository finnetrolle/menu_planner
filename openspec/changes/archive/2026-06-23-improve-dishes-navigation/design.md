## Context

Экран [src/pages/DishesPage.tsx](/Users/finnetrolle/dev/menu_planner/src/pages/DishesPage.tsx) сейчас показывает карточки блюд, поддерживает только поиск по названию и рассчитывает КБЖУ на клиенте на основе `useDishes`, `useIngredients` и `calculateCalories`. При росте числа блюд пользователь не может быстро отсортировать список по пищевой ценности, отобрать блюда по диапазонам КБЖУ или быстро вернуться к полному каталогу после применения нескольких ограничений.

В соседнем экране ингредиентов уже есть понятный паттерн клиентской сортировки, но он заточен под табличное представление. Для блюд нужно сохранить текущий карточный layout и встроить в него отдельную панель навигации по списку.

## Goals / Non-Goals

**Goals:**
- Дать пользователю быстрый и предсказуемый способ сортировать блюда по названию, весу, калориям, белкам, жирам и углеводам.
- Добавить фильтрацию по поиску и диапазонам КБЖУ без изменения текущих CRUD-сценариев.
- Сохранить все вычисления на клиенте и не расширять Tauri API без необходимости.
- Сделать состояние списка самодостаточным: пользователь должен видеть активные фильтры, количество найденных блюд и иметь быстрый сброс.

**Non-Goals:**
- Перенос сортировки и фильтрации на backend или в SQLite-запросы.
- Изменение схемы БД, команд Tauri или формата `DishWithId`.
- Переработка карточек блюда, диалога редактирования блюда или экрана планировщика меню.
- Постоянное сохранение пользовательских фильтров между запусками приложения.

## Decisions

### 1. Derive a normalized dish list view model in `DishesPage`

Решение:
Создать в `DishesPage` мемоизированную производную коллекцию элементов списка, где для каждого блюда заранее рассчитываются:
- `nutrition` (`calories`, `protein`, `fat`, `carbohydrates`)
- `weight` как число или `null`
- вспомогательные флаги для рендера и сортировки

Почему:
- Сейчас КБЖУ считаются прямо во время рендера карточки, что неудобно для повторного использования в сортировке и фильтрах.
- Один нормализованный view model позволит сначала вычислить данные, а затем единообразно применять поиск, фильтры и сортировку.

Альтернативы:
- Считать значения заново в comparator и filter-предикатах. Отклонено, потому что это дублирует логику и усложняет поддержку.
- Запрашивать агрегированные КБЖУ из backend. Отклонено, потому что задача локальная для UI и не требует расширения API.

### 2. Keep sort and filter state local to the page

Решение:
Добавить локальные состояния страницы:
- `sortField`
- `sortDirection`
- `searchQuery`
- `filters` с необязательными минимумом/максимумом для калорий, белков, жиров и углеводов
- `isFilterPanelOpen` для мобильного и компактного режима

Почему:
- Эти настройки нужны только для управления текущим представлением списка.
- Локальное состояние делает решение изолированным и не ломает текущие React Query hooks.

Альтернативы:
- Хранить состояние в query string или глобальном store. Отклонено, потому что в приложении нет route-based navigation, а задача не требует межстраничного шаринга состояния.

### 3. Use a two-level navigation UI above the card grid

Решение:
Добавить над карточками блюд:
- строку быстрого доступа с поиском, селектом сортировки, переключателем направления и кнопкой добавления блюда
- раскрываемую панель фильтров с диапазонами для калорий, белков, жиров и углеводов
- строку состояния с количеством найденных блюд, активными фильтрами и кнопкой сброса

Почему:
- Карточный layout удобнее сохранять, чем переводить экран в таблицу.
- Поиск и сортировка должны быть доступны всегда, а более плотные числовые фильтры можно прятать в отдельную панель, чтобы не перегружать экран.

Альтернативы:
- Полностью табличный вид, как у ингредиентов. Отклонено, потому что это меняет характер экрана и потребует более крупной UI-перестройки.
- Модальное окно фильтров. Отклонено, потому что для локального перебора фильтров лучше подходит инлайн-панель с моментальной обратной связью.

### 4. Apply filters client-side in a stable processing pipeline

Решение:
Обрабатывать список в одном `useMemo` в таком порядке:
1. нормализация блюд и расчёт КБЖУ
2. текстовый поиск по названию
3. диапазонная фильтрация по КБЖУ
4. сортировка итогового набора

Почему:
- Такой порядок даёт предсказуемый UX и упрощает тестирование.
- Фильтры работают на уже вычисленных данных и не зависят от порядка рендера карточек.

Альтернативы:
- Применять сортировку раньше фильтров. Отклонено, потому что пользователь ожидает порядок внутри уже отфильтрованной выборки.

### 5. Validate filter input softly

Решение:
Пустые границы диапазона трактовать как отсутствие ограничения, а при невалидной паре `min > max` показывать понятное состояние ошибки около конкретного фильтра и не применять только этот диапазон до исправления.

Почему:
- Это безопаснее, чем автоматически менять местами значения и создавать скрытую магию.
- Пользователь получает прозрачную обратную связь без сброса остальных фильтров.

Альтернативы:
- Автоматически менять местами минимум и максимум. Отклонено, потому что это может неожиданно исказить намерение пользователя.

## Risks / Trade-offs

- [Рост локальной UI-сложности] → Сгруппировать новую логику в небольшие локальные типы и вспомогательные функции внутри `DishesPage` или рядом с ним, чтобы страница не превратилась в монолит.
- [Повторный расчёт КБЖУ для длинного списка] → Считать nutrition один раз в мемоизированном view model и переиспользовать его во всех стадиях обработки.
- [Перегрузка mobile-layout числовыми полями] → Разместить фильтры в раскрываемой панели и использовать адаптивную сетку из 1-2 колонок.
- [Несогласованность UX между экранами ингредиентов и блюд] → Переиспользовать существующий визуальный язык контролов и иконок сортировки, но не копировать таблицу в карточный экран.
